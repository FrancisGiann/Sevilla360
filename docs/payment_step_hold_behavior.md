# Payment-step inventory hold

Apply `migrations/036_payment_step_hold.sql` after the production-applied `035_dual_channel_recovery.sql`, before deploying this code. This repository has no automatic migration runner; verify the target schema and record the manual migration receipt. Migration 036 was applied twice successfully in a disposable MariaDB fixture, but has not been applied to production.

Online hotel and villa date selection remains nonexclusive. Opening payment first locks the booking and all physical venue rows, checks overlapping bookings, add-ons, maintenance, seminars, and active staff/customer locks, then creates a 15-minute hold. Account and QR details are returned only after that transaction commits. A concurrent loser receives method names only, with a warning to avoid a new transfer and a receipt path for money already sent. Reopening with the same token does not extend the timer.

Back, Cancel, modal close, and navigation release an unsubmitted hold. A durable exit token prevents a delayed acquisition response from recreating a hold after exit; an old tab cannot release a newer token or a submitted proof claim. Browser crashes, offline exits, and interrupted requests may delay release, so the server expiry remains the fallback. Payment instructions already copied or saved outside the site cannot be revoked.

Submitting proof within a valid hold consumes the short lock and promotes the booking to the existing pending-review claim. Pending review retains inventory even after the old payment deadline. The first staff rejection opens one fresh 24-hour correction window; submitting the one permitted retry does not reset it; a second rejection releases the date. A late, stale, or conflicting receipt is preserved for staff reconciliation without reserving occupied inventory. The system does not automatically refund an external transfer.

Another active hotel/villa booking screen polls advisory availability every 10 seconds while visible, and refreshes on focus. It shows a temporary-hold notice, then an unavailable notice after a proof claim, and offers a room/date change or recheck. The server always revalidates when acquiring the payment hold. The read-only poll returns only `available`, `held`, or `unavailable`; it sends no customer identity, payment account, QR, or hold token.

The payment dialog is shared by `booking.php` and `user_dashboard.php`. `get_my_booking_details.php` omits the internal payment-step token. Active locks are checked by online and walk-in booking, seminar allocation, blocking maintenance, and venue availability changes. Browser UI screenshots were unavailable in the isolated fixture; synthetic MariaDB tests cover concurrent acquisition, multi-resource and villa overlap, Back/reentry, stale exits, promotion, and expiry races.
